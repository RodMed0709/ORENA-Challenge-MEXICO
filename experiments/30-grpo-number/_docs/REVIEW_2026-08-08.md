## 🔴 BLOCKING — `_assert_learned` reports success when it cannot find its instrument

`_models/grpo_train.py:235-237`

```python
logs = sorted((cfg.run_dir / "ckpt").glob("*/logging.jsonl"))
if not logs:
    return {"checked": False, "reason": "no logging.jsonl under ckpt/"}
```

`_models/grpo_train.py:340` raises only on an `"error"` key:

```python
if err := result["training_check"].get("error"):
```

⇒ A run whose log lands anywhere else — a layout change in ms-swift, a different `output_dir`, a
relaunch into a fresh directory — **passes the guard silently**. That is precisely the failure
class this guard exists for: an instrument that cannot measure reports OK.

It did not bite on either full run because both wrote where expected. It is blocking anyway,
because the guard's whole value is being trustworthy when nobody is watching.

**Fix:** treat `checked: False` after `rc=0` as a raise.

## ⚖️ Ruling requested by `fa811ab` — CONSTITUTION §IV.2 vs "checkpoint-600 vs checkpoint-600"

`fa811ab` declared clause 1 (the verdict pair is `checkpoint-600` vs `checkpoint-600`) and
explicitly left the §IV.2 tension for the review to rule on. Ruling:

**§IV.2 does not bind clause 1. Clause 1 stands.**

§IV.2 reads *"Every improvement is validated against OOD, not just ID. Report acc-ID and acc-OOD at
every checkpoint. **Discard the one that wins ID but loses OOD.**"* The operative verb is
*discard* — it governs **which checkpoint you keep**, i.e. selection for shipping. Rung 30's claim
is not *"this checkpoint is better than A2, ship it"*; it is *"the RL objective beats step-matched
SFT"*. OOD-selecting within each arm would let the two arms land on different step counts, which
destroys the step-matching that is the rung's entire design.

🔑 **And §IV.2 is not being bypassed — it is satisfied by a different clause.** The OOD validation
it demands already lives in the win condition: `S8` clause 2 requires the result to hold on **ID
and OOD jointly**, and names `aggregation_OOD` as unable to move against us. Rung 30 reports both
sides and can be vetoed by the OOD side. That is what §IV.2 is for.

🔴 **Caveat, and it must be written down before it is convenient:** §IV.2 binds **fully** the
moment a rung-30 checkpoint is considered for shipping. Selection-for-shipping is a separate
decision from adjudication and must not be smuggled into it. If `checkpoint-600` wins and a
different checkpoint is later preferred on OOD grounds, that is a new decision with its own
record — not a re-reading of this one.

## 🟡 Non-blocking

### 1 — `_assert_learned` bounds direction, not magnitude

`grpo_train.py:228-256` tests `grad_norm > 0` on ≥50% of logged steps. That separates *gradient* from
*no gradient*; it cannot separate *moved* from *barely moved* at any nonzero LR. The discriminator
that actually separates the cases — `sum|Δ|`, measured at **189×** and written up at
`grpo_train.py:44-49` — exists in prose only. Wiring a `sum|Δ|` floor against the starting adapter
would make the check a property of the run rather than a number computed once by hand.

### 2 — "byte-for-byte" is false; the reward is stricter than the shipped container

`grpo_reward.py:38` claims the container's repair *"byte-for-byte:
submissions/02-rung21-a2/inference.py:337-367"*, and `:43` uses `r"^(\d+)\.$"`. The container
(`submissions/02-rung21-a2/inference.py:333`) uses `r"^(\d+)\s*\.$"` — it tolerates whitespace
before the period. So `"3 ."` is **repaired in deployment and scored 0 in training**. Low
frequency, but the reward under-credits relative to what ships, and the claim as written is wrong.

### 3 — The collapse guard still has no implementation

`README.md:59-61`: with `beta = 0`, the `S8(c)` veto moves from the loss to the protocol —
*"frequent checkpoints with `object_recognition` scored at each"*. `fa811ab` fixed **which**
checkpoint decides, which was the sharper hole. But nothing in the code schedules, runs or gates
that evaluation: `save_steps=100` writes the checkpoints and the scoring remains manual. `S8(c)`
is a blocking clause, so the veto currently depends on someone remembering.

### 4 — Step-matching is now empirically confirmed but still asserted nowhere

`CONTEXT.md` records both arms at **600 optimizer steps** with six checkpoints each, so the
premise holds for this run. It holds by observation, not by construction: `num_train_epochs = 1.0`
for both arms (`grpo_train.py:147`), and GRPO's step accounting with `num_generations = 8` is not
the same arithmetic as SFT's. Record both counts and assert equality before the comparison.

### 5 — Hard-coded cross-checkout paths

`_tools/build_number_subset.py:85` writes to
`/workspace/repo_rodri/experiments/30-grpo-number/runs/30_grpo_v1`, while `grpo_train.py:81,95`
self-locate via `EXP = Path(__file__).resolve().parent.parent`. On any other checkout the trainer
reads a path the builder never wrote. This is rung 17's defect verbatim (`context/NOW.md`,
2026-07-31: *"a hard-coded `exp_dir` that would write another checkout"*). `CONTROL_TRAIN:68` and
`A2_CKPT:82` point at a third checkout, `/workspace/repo`.

### 6 — `_smoke_slice` raises `RuntimeError` on a short file

`grpo_train.py:172`: `lines = [next(fh) for _ in range(cfg.smoke_rows)]`. `StopIteration` inside a
comprehension surfaces as `RuntimeError` when the file has fewer than `smoke_rows` lines. Use
`itertools.islice`.

### 7 — The 50% threshold collides with GRPO's own zero-advantage rate

Step 5 measured `zero_advantage` **0.280 / 0.270**, and this rung measured `frac_reward_zero_std`
≈ **0.30** — three of ten steps carry no gradient. It passes today at ~70%, but as the policy
improves the reward saturates and the zero-advantage rate rises. A converged GRPO run could trip
the guard and raise after a legitimate 2h40. Consider per-arm thresholds.

## Related, not a finding — a premise of this rung has been re-measured

The reward is 0/1 exact match against the `number` gold, so gold stability is a premise. The
`±0.86` label-noise figure in `context/ERROR_ANATOMY.md:137-148` **does not reproduce**: its `gap`
column is the true gap in seconds divided by the video fps, so its sub-second buckets describe
pairs that are in fact 12–25 s apart. At the corpus's true minimum separation of 1 s (n=461), the
gold moves **0.384** and changes in **29.9%** of pairs, against 0.86 / 56.6% as published.

This **strengthens** rung 30 — the reward signal is about half as noisy as the repo claimed, and it
is consistent with step 5's 24pt headroom, which a model sitting at its label's noise floor could
not have. Recorded here only because it touches this rung's premise; it changes nothing above.
