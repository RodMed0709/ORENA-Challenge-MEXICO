## The headline

**The container produced a real `answer.json` for the first time in its history.** Before today
the only pre-submission test was a CPU smoke of startup and model load — submission 01 was
uploaded having never emitted an answer file.

```
batch.json: batch_size=3 qIDs=3 layout={'frames': 'frames/<qID>.png'}
Frames: 3 from DECLARED layout 'frames/<qID>.png' -> /input/frames
Model ready on cuda:0 (setup 31.86 s)
```

corroborates the 0.79 s/question amortized cost recovered from the platform's own metrics.

## Fixes shipped

| # | Defect | Fix | Proven by |
|---|---|---|---|
| 1 | `batch.json` never read — the platform *declares* the frame layout and we guessed | `read_batch_manifest()`; `layout.frames` is authoritative, old heuristics are the fallback, plus a last-resort `/input` sweep | pod run logs the declared layout and uses it |
| 2 | `rglob("*.png")` is case-sensitive on Linux → `.PNG` = empty index = score **exactly 0.0000** | case-insensitive across png/jpg/jpeg/bmp/webp; duplicate stems logged | pod variant A: `.PNG` indexes 3/3, same answers |
| 3 | Systematic frame failure exited 0 with an `answer.json` of empty strings | abort **before** loading 17 GB (exit 2); if >half the questions raise, write `answer.json` then exit 3 | pod variant C: exit 2, no weight load, no file |
| 4 | Silent CPU fallback (measured: >35 min for one question) | hard `RuntimeError` unless `ALLOW_CPU=1` | code + local scenarios |
| 5 | Unguarded ZIP extraction killed the run with no `answer.json` | `try/except`, degrade to the next candidate | local scenario 7 |
| 6 | `batch_size` never cross-checked | warn on mismatch, `request.json` wins | pod run |
| 7 | Deps were floors, not pins | exact pins for the three that change behaviour; bounded ranges for the three that only need torch compatibility | — |

Plus a Dockerfile build-time assertion: `pip install --user` writes to `~/.local`, which shadows
the base image's site-packages, so a transitive dependency could silently replace the CUDA torch
build and nothing would notice until the container was scored. The build now fails if torch loses
CUDA or leaves the 2.5 line.

**Local:** 7/7 adversarial layout scenarios pass (official fixture, UPPERCASE, jpg-under-png,
nested ZIP, no manifest, undeclared layout, corrupt archive).

## Accidental finding worth keeping

A mis-globbed fixture path pulled another track's `batch.json`, which declares
`layout={'plain': 'plain/<qID>.mp4', 'overlayed': 'overlayed/<qID>.mp4'}` — **videos, and no
`frames` key at all**. The hardened code handled it exactly as designed: no `frames` key → sweep →
no images → abort with exit 2 instead of writing empty answers. An unplanned validation of the
unknown-layout path, and a hint that `layout` is a general mechanism across tracks.

## Limitations, stated

- **Docker was not exercised.** RunPod pods have no Docker daemon, so this ran the container's
  *logic* under the pod's env (`torch 2.8.0+cu128`), not its image (`pytorch/pytorch:2.5.1-cuda12.4`).
  The `Dockerfile` was separately verified byte-identical to the template's, so the residual risk
  was in `inference.py` — which this covers. A real `docker build` + `do_test_run.sh` on a machine
  with Docker is still unrun.
- **The pins are declared, not observed in-container.** Versions came from the pod env; the image
  resolves its own against torch 2.5.1. The new build assertion is what turns a bad resolution into
  a build failure instead of a scored submission.
- **The judge mismatch is untouched** — acknowledged by the user as a limitation. 29% of the
  `object_recognition` ID bucket is judge-scored; the SDK default `Qwen/Qwen3.5-4B` does not exist
  on HF, we use `Qwen3-4B`, the platform uses something undocumented.
- **Not versioned:** `do_build.sh` / `do_save.sh` / `do_test_run.sh` and `resources/`. The template
  ships them and their absence is exactly why the validating step was skipped — but `CLAUDE.md`
  forbids `.sh` launchers. Left for the user to rule on.
