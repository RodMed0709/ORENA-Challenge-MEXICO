# Submission 03 — "Qwen3VL + A2 + Conector + OOD" (rung 42, merged corpus)

> The build recipe **minus the 17 GB of weights**. `resources/model/` is regenerated by the
> merge command below; everything else needed to rebuild is in this folder.
>
> **Checkpoint decided: epoch 4, `checkpoint-4848`**, by the held-out sweep in
> `experiments/42-merged-corpus/01_eval_heldout.ipynb` (2026-08-15). Not the last epoch —
> see the memorisation read below, which is the reason all five were scored.

## What is being shipped

**Rung 42**: Qwen3-VL-8B-Instruct + LoRA on the ViT, the LLM **and the ViT→LLM connector**
(`visual.merger.linear_fc{1,2}` + the three `deepstack_merger_list` blocks, named
explicitly — [[the-merger-is-unreachable-by-default]] measured that `all-linear` reaches
the connector in *neither* ms-swift nor Unsloth, so the module list is load-bearing and not
decoration). lr 2e-4, rank 8, α 32, dropout 0.1, `freeze_vit false`, `freeze_aligner false`,
cosine, seed 42 — the A2 recipe, verified from the emitted `args.json` and not from memory.

**Five epochs on a merged corpus of 19,384 rows**: rung 18's 14,415 (count-aug) plus 4,969
rows generated from **30 of the 38 public test videos**, promoted into training.

## 🔴 Read this before quoting any number from this package

Training on our own public test videos is legal — the hidden leaderboard set (20 videos) and
the final test (200 videos) are untouched by the merge, and that is the entire point of
making the trade. **What it costs is the local instrument.**

`RESULTS_split_42.json` promoted **8 of the 10 `heico` test videos into training**, so
**Sigmoid Resection — the challenge's out-of-distribution procedure — is inside this model's
training set.** Only 8 videos were held back:

| held out | n videos | n questions |
|---|---|---|
| `heico` (`0023`, `0027`) | 2 | 800 |
| `lapchole` | 6 | 483 |
| **total** | **8** | **1,283** |

⇒ every `*_OOD` cell reported for this checkpoint means **unseen VIDEO of a SEEN
procedure**, not unseen procedure. `RULES §3` — "ID/OOD ALWAYS from the qID prefix" — is a
faithful reconstruction of the organizers' design for every *other* rung and **does not hold
for this one**. `frame.metrics` still prints the `OOD` label because forking the canonical
scorer for one rung is what `RULES §1` forbids; the correction travels in writing, in the
notebook, in `RESULTS_heldout_eval.json.ood_caveat`, and in the
`ood_procedure_in_train=True` column of `RESULTS.csv`.

Second consequence, equally binding: **effective n is 8 videos** (`RULES §13`), two of them
on the heico side. No heico confidence interval in this rung is readable. A jackknife over
videos moves `acc_OOD` by a median 0.024 on *38* videos; on 2 it is not an instrument.

## The bar it has to clear

A2 (`21_lr_2e4_v1`) never trained on any test video, so its archived answers are valid on
these 8 videos with no re-inference and no GPU-swap drift. Restricted to the same 1,283
qIDs, scored through the same `frame.metrics.stratified_report`:

| A2 epoch | `bucket_mean` | `acc_ID` | `acc_heico` |
|---|---|---|---|
| 1 | 0.5282 | 0.5404 | 0.5112 |
| 2 | 0.6104 | 0.6356 | 0.5800 |
| **3 (the incumbent, submission 02)** | **0.6342** | 0.6646 | 0.5988 |

(For orientation: A2 ep3 scores `bucket_mean` 0.6496 on the full 6,252 and **0.5288 on the
real leaderboard**, rank 11. Local numbers run high and invert on OOD —
[[local-eval-vs-judge-calibration]]. Use the sign, deflate the magnitude, never quote the
local level as a leaderboard prediction.)

**Selection axis, declared before the run:** `bucket_mean` on the held-out set, ID and heico
weighted equally, which is what the final Copeland ranking does (`RULES §4c`). `RULES §6`'s
`acc_OOD` axis does not exist for this rung.

**Memorisation read, also declared up front:** training reached `token_acc` **0.987** on
train by epoch 5. The signature of memorisation is held-out accuracy that *rises and then
falls*. If it appears, the selected checkpoint is the peak — never the last epoch.

Read honestly against `RULES §S8`: the pre-declared cell wins, **no cell shows significant

## Rebuilding

### 1. On the pod (GPU) — regenerate the weights

```
swift export \
  --adapters /workspace/repo_rodri/experiments/42-merged-corpus/runs/42_merged_v1/ckpt/v0-20260814-163049/checkpoint-4848 \
  --merge_lora true \
  --output_dir  /workspace/repo_rodri/experiments/42-merged-corpus/runs/42_merged_v1/merged/checkpoint-4848
```

~2 min, ~17 GB (measured on this rung's own sweep — the 9 min in submission 02's README was
an A100 under three-pod MooseFS contention, not the cost of the operation).

The merged dir must contain `config.json`, `preprocessor_config.json`, `tokenizer_config.json`,
`chat_template.jinja` and `generation_config.json` — `inference.py` calls
`AutoProcessor.from_pretrained(MODEL_PATH)`, so copying only `*.safetensors` builds a 17 GB
image that dies at startup.

⚠️ Use **this** command, not `peft.merge_and_unload`: it is the same function the evaluation
used, and the only one known to handle the ViT-side adapters and the connector modules the
way the scored run did.

### 2. Locally (Docker) — build, smoke, save

Docker does **not** run on a RunPod pod (it is itself a container: no binary, no socket). The
pod is the weight factory; the image is built on a normal machine.

```
# put the merged dir at resources/model/, then:
python test_normalize_answer.py   # answer-boundary gate, no GPU, no Docker — run it FIRST
./do_build.sh                     # docker build --platform=linux/amd64 --tag frame-algorithm .
./do_test_run.sh                  # offline smoke against test/input — CPU is fine and expected
./do_save.sh                      # docker save frame-algorithm | gzip -c > frame-algorithm*.tar.gz
```

Upload the tarball, **wait for "import completed"**, then Submit.

🔴 **Disk warning, this machine specifically.** The Docker Desktop `vhdx` on `C:` grows and
**never shrinks**. A 17 GB build context has killed the daemon here before, and the first
container run costs ~17 GB again. Check free space on `C:` before `do_build.sh` and treat
this as a deliberate, supervised step — not something to fire and walk away from.

## What changed from submission 02's package

| # | change | why |
|---|---|---|
| 1 | `build_frame_index` **iterates every `layout` key** instead of reading `layout["frames"]` | `frames` is FRAME's key. The SEGMENT track declares `plain`/`overlayed` and **no `frames` key at all**. A rename we are not told about produced an empty index and a silent all-empty `answer.json` — the exact failure mode that cost submission 01 a slot, one level deeper |
| 2 | **every `/input/*.zip` is a candidate**, `batch-frames.zip` first; each extracts to its own subdir | 02 hard-coded the archive NAME. Assuming the name is the same bug as assuming the directory. Per-archive extract dirs stop two same-stem archives from overwriting each other |
| 3 | **`clamp_class_tokens`** — `fo_class` vocabulary read from `FOType.names()` **at runtime** | `RULES §8b`. An unrecognised class token does **not** score 0 — `FOClass.verify` **RAISES** and takes the whole answer down. The prompt's 10-item list and the scorer's 10-item list disagree on their 10th element (`foreign object` vs `Absorbable Hemostatic Agent`), so any hard-coded copy is a guess about which document the scorer follows |
| 4 | the test file now also gates the clamp, against the SDK's **real** `FOClass` registry | it asserts both halves: illegal tokens are rescued, and **22 other inputs come back byte-identical**. The identity half is the safety gate — this code runs on every answer |
| 5 | every `A2`/`rung 21` string → rung 42, plus the OOD caveat in the module docstring | the startup log line is the **only** artifact you get back from a run that dies early |

Unchanged and deliberately so: `MAX_FAILED_FRACTION = 0.5` (at B=20 a 0.05 threshold rounds
to ONE question — two unlucky failures would discard eighteen good answers), the warm-up
inference, the widened build guard, `numpy<2.0`, and `normalize_answer`.

### 🔴 Known defect, shipped deliberately

`inference.py:553` logs `=== ORena SAVE FOCUS FRAME — rung 21 arm A2 (lr 2e-4, ep3)
inference start ===`. **The startup line names the wrong rung.** It is a label only — it
touches no answer, no format and no score — but submission 02's own README calls this line
"the ONLY artifact you get back from a run that dies early", so it is a real cost if this
container ever fails early on the platform.

Not fixed because the fix is not cheap: BuildKit re-transfers the whole 17 GB context on
**every** `docker build` invocation (~14 min, measured three times, cache warm or not), and
`do_save.sh` re-invokes `do_build.sh`, so correcting one string costs a rebuild plus a
~19 min single-threaded gzip — ~50 min for zero points. Fix it in the next package.

## What is NOT verified

- **The GPU path inside the image.** Never exercised live, for submissions 01 or 02 either.
  No local GPU is large enough (~16.5 GB) and the pod has no Docker.
- **Numerics across hardware.** The eval ran on an A100; the image is torch 2.5.1/cu124 on
  an L40S. [[archived-results-not-bit-reproducible]] prices a GPU swap at ~0.5 % of answers.
- **The container-vs-eval reproduction.** Submission 02 measured 56/60 byte-identical and a
  **+0 delta** in correctness with this same `inference.py` generation path. That check has
  **not** been re-run for rung 42's weights, and items 1–3 above changed the input and
  answer boundaries — the unit test covers them, a live container run does not yet.
