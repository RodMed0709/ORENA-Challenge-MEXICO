# Submission 02 — rung 21 arm A2 (`21_lr_2e4_v1/checkpoint-2703`)

> The build recipe **minus the 17 GB of weights**. `resources/model/` is regenerated by the
> merge command below; everything else needed to rebuild is in this folder.

## What is being shipped, and what it is NOT

**Rung 21 arm A2**: Qwen3-VL-8B-Instruct + LoRA on ViT and LLM, **lr 2e-4**, rank 8, α 32,
three epochs, trained on **rung 18's `train.jsonl` (count-aug)** — used in place with its
sha256 asserted.

⚠️ **This is not "rung 06 at a different learning rate".** The training data differs too:
rung 18 added 667 minted zero-count rows and question-surface variation on top of rung 06's
corpus. Submission 01 shipped rung 06 (no minted zeros, lr 2e-5, epoch 2).

Offline scores on the full 6,252, epoch-matched (`experiments/21-recipe-sweep/RESULTS_A2_lr.csv`):

| | value |
|---|---|
| leaderboard proxy `mean(aggregation_ID, object_recognition_ID)` | **0.6104** |
| `bucket_mean` (our 4-cell headline — **not** what the platform scores) | 0.6496 |
| `margin_OOD` | 0.2343 |

Against submission 01's rung 06 (`bucket_mean` 0.5724 local, 0.4710 mean-ID on the platform).

⚠️ **A2's advantage is not statistically significant on the ID-only cell the proxy is made
of** (+0.0221, CI [−0.0017, 0.0449] vs arm A). It is significant on `ALL`, `OOD` and
`fo_class ID`. Read `context/decisions/recipe-axis-is-the-learning-rate.md` before quoting
this as a measured lead over arm B, which it is not.

## Rebuilding

### 1. On the pod (GPU) — regenerate the weights

The evaluation deletes its own merge to reclaim 17 GB (`21b` runs `KEEP_MERGED=False`), so the
exact bytes that scored 0.6104 do not exist on disk. They are **reproducible** — measured, not
assumed: two independent merges came out byte-identical on 2026-07-30.

```
swift export \
  --adapters .../21-recipe-sweep/runs/21_lr_2e4_v1/ckpt/v0-20260729-172404/checkpoint-2703 \
  --merge_lora true \
  --output_dir .../21-recipe-sweep/runs/21_lr_2e4_v1/merged/checkpoint-2703
```

~9 min, 17 GB. Reference hash of the merged manifest: `b3fc1be40bd7a4ad0db08713337853f1…`.

⚠️ Use **this** command, not `peft.merge_and_unload` — it is the same function the evaluation
used, and it is the only one known to handle the ViT-side adapters and the two excluded merger
modules the way the scored run did.

The merged dir must contain `config.json`, `preprocessor_config.json`, `tokenizer_config.json`,
`chat_template.jinja` and `generation_config.json` — `inference.py` calls
`AutoProcessor.from_pretrained(MODEL_PATH)`, so copying only `*.safetensors` builds a 17 GB
image that dies at startup.

### 2. Locally (Docker) — build, smoke, save

Docker does **not** run on a RunPod pod (it is itself a container: no binary, no socket). The
pod is the weight factory; the image is built on a normal machine.

```
# put the merged dir at resources/model/, then:
./do_build.sh      # docker build --platform=linux/amd64 --tag frame-algorithm .
./do_test_run.sh   # offline smoke against test/input — CPU is fine and expected
./do_save.sh       # docker save frame-algorithm | gzip -c > frame-algorithm.tar.gz
```

`do_test_run.sh` uses `--gpus all` only if Docker exposes an NVIDIA runtime, and otherwise
runs on CPU on purpose: *the platform always provides a GPU*. Upload the tarball, **wait for
"import completed"**, then Submit.

## 🔴 The one thing to remember: the frame interface is ambiguous

The platform's algorithm-interface page declares `batch-frames` as **Kind: ZIP file** at
**`/input/batch-frames.zip`**. The organizers' own template documents
**`/input/frames/<qID>.png`** and ships a plain-directory fixture. They disagree and it cannot
be settled before a real run.

`inference.py` therefore resolves in order: `batch.json`'s declared layout → `frames/` →
`batch-frames.zip` → a full `/input` sweep → abort. The index is keyed by qID via `rglob`, so
nesting inside the archive is harmless, and `log_input_inventory()` runs **before** the weight
load so a failed run names its own cause.

**Why it matters.** The per-question `except` emits an empty answer so one bad question cannot
cost the batch. With the wrong layout that safety net becomes a **complete `answer.json` of
empty answers** — a silent zero that burns a slot.

## What changed from submission 01's package

| # | change | why |
|---|---|---|
| 1 | `MAX_FAILED_FRACTION` **0.5 → 0.05** | at B=2000 the old value permitted **1000 empty answers and exit 0** — a schema-valid half-zero. A real run has ~0 failures |
| 2 | **warm-up inference** before the timed loop | `run.py` does this and says why: ~11 s cold vs ~0.3 s warm. Without it question 1 is timed with CUDA-graph capture still ahead of it, against a 5 s gate |
| 3 | build guard widened past torch | it asserted **only** torch: it printed the transformers version without checking it and never imported `qwen_vl_utils`, `focus` or `torchvision`. Now all five are asserted |
| 4 | `numpy` **`<3.0` → `<2.0`** | `<3.0` resolves numpy 2.x onto a torch-2.5.1 base predating numpy-2 hardening, and nothing asserted it |
| 5 | every `rung 06` string → A2 | including the startup log line, which is the **only** artifact you get back from a run that dies early |
| 6 | `resources/` documented as the merged dir | the Dockerfile still described the template's `model.py` + `dummy_weights.pt`, which this package does not use |

## Fidelity to the scored checkpoint

Same system prompt (byte-identical to `src/frame/engine.py`), same `max_pixels` 1280×720, same
`max_new_tokens` 64, same greedy path, same 300-char cap.

⚠️ **One deliberate difference, stated so nobody calls this byte-identical again:**
`normalize_answer()` runs here and did **not** run in the evaluation
(`cfg.answer_postprocess is None`). It repairs a trailing period on a bare integer or on
yes/no — strings the SDK's `Number.verify` (`strip().isdigit()`) and `Binary.verify` score as
wrong regardless. Measured on A2 ep3's own answers: **110 strings carry a trailing period and
all 110 are `open_ended`**, where the gold carries the period too — so the repair fixes 0 of
the 44 wrong ones and touches 66 currently-correct ones.

🟢 **What that costs was measured, not argued.** A paired A/B under the same judge and seed,
scoring each of the 110 as committed and again with the period stripped
(`experiments/21-recipe-sweep/RESULTS_period_judge_ab.csv`):

| | correct |
|---|---|
| with period (as scored) | 66 / 110 |
| period stripped (as the container sends it) | 66 / 110 |
| **verdicts flipped** | **0** |

The judge is indifferent to the punctuation. The normalisation stays because it costs a
measured zero here.

Its value is insurance against the **hidden** test, not against ours: probe 16a measured 87% of
`number` answers taking the `"1."` shape on off-template questions, and our scored eval only
ever asks the corpus's own templates — so a formatting fragility outside them is invisible to
every number we report, by construction.

## 🟢 The check nobody had ever run: does the shipped code reproduce the scored model?

Every earlier verification tested *wiring* — the container starts, finds frames, writes valid
JSON. None tested whether the model inside is the model that scored 0.6496.

Method: build a real `/input` in the container's own shape (`request.json` + `batch.json` +
`FO_definitions.json` + `frames/<qID>.png`) from A2 epoch 3's committed run, run **this exact
`inference.py`, unmodified**, on the merged weights on a GPU, and diff against `inspect.csv`.
60 questions, stratified by `answer_format`, sampled at random (`RESULTS_container_vs_eval.csv`).

| | |
|---|---|
| answers byte-identical | **56 / 60 (93.3%)** |
| eval correct | 36 / 60 (60.0%) |
| **container correct** | **36 / 60 (60.0%)** |
| **delta** | **+0** |

Of the 4 that differ: 1 favours the eval, 1 favours the container, 1 both wrong, 1 both right
in different words. **An exact split.**

⚠️ It is not byte-identical and cannot be: the eval decodes frames with decord straight from
the video, the container reads PNGs — which is what the platform actually hands it. That
difference predates us; it is already inside submission 01's 0.4767.

⚠️ Two sampling traps this ran into, both worth remembering. **Taking the first N rows of a
file is not a sample** — the first 50 rows of `inspect.csv` are 0% correct against a corpus
that is 67% correct, so the run compared the two systems only on the questions the model is
least sure about, where any input difference flips the answer. It read 82% and looked alarming.
And the SDK ships FO definitions as **`assets/FO_definitions.txt`**, not `data/*.json`; missing
them changes the system prompt silently, because the text is pasted into it verbatim.

## What is NOT verified

- **The GPU path inside the image.** Never exercised live, for submission 01 either. There is
  no local GPU large enough (the model needs ~16.5 GB) and the pod has no Docker. The
  generation code is unchanged from the engine that ran 6,252 questions on GPU.
- **Numerics across hardware.** The eval ran torch 2.8.0+cu128 on an RTX 5090; the image is
  torch 2.5.1/cu124 on an L40S. `archived-results-not-bit-reproducible` prices a GPU swap at
  ~0.5% of answers changing.
- **Image provenance.** Training fed q95 JPEGs, the eval feeds decoded frames, the container
  reads PNGs. Pre-existing and shared with submission 01.
